# 엑셀 권한 테이블 확인과 3역할 설계안

작성일: 2026-10-27. 이 문서는 당시 두 엑셀과 코드에 대한 조사 및 제안이다. 이후 구현 상태와 운영 제약은 [로그인·권한·감사](로그인_권한_감사.md)를 참고한다.

## 1. 두 파일 확인 결과

| 자료 | 확인한 범위 | 결과 |
| --- | --- | --- |
| `조선_AX_목업데이터.xlsx` | 전체 17개 시트: 요약, 필드사전, 업무 데이터 15개 시트의 이름·헤더·셀 | 계정, 역할, 권한 부여, 로그인 또는 관리자 권한을 저장하는 테이블과 필드가 없다. `status_codes`는 작업·설비·사건·검사·재작업의 상태코드다. |
| `01_조선_데이터참고명세서.xlsx` | 전체 10개 시트, 특히 `데이터구성`, `테이블관계`, `항목명세`, `구현참고` | 계정이나 권한 테이블 명세는 없다. `구현참고!B10`은 조회자·작업담당·관리자의 권한을 제안하며, `구현참고!B11`은 실제 사용자 계정을 포함하지 않았다고 명시한다. `자료안내!B11`은 권한 설계를 개발환경과 협의하도록 안내한다. |

목업의 `work_orders.team_id`는 작업조 식별값이고 `incidents.owner_team`은 사건 담당조 명칭이다. 사용자의 로그인 계정이나 역할을 나타내지 않는다. 실제 샘플은 전자에 `TEAM-01`~`TEAM-06`, 후자에 `자재조-A`·`정비조-A`·`품질조-A`를 사용하므로 두 필드를 같은 키로 가정해 자동 연결하지 않는다.

현재 실행 화면의 역할 선택은 브라우저 변수이며, [서버 API](../app/backend/Program.cs)에는 인증·역할별 인가가 없다. 따라서 기존 화면 선택만으로는 관리자 권한을 안전하게 부여할 수 없다.

## 2. 역할별 권한 제안

명세의 제안을 출발점으로 하며 실제 담당 범위와 운영 정책은 확정이 필요하다. 하나의 활성 계정에는 아래 역할 하나를 부여한다.

| 기능 | 조회자 `VIEWER` | 작업담당자 `WORKER` | 관리자 `ADMIN` |
| --- | --- | --- | --- |
| 운영현황·조회·상세 읽기 | 허용 | 허용 | 허용 |
| 담당 작업의 실적·사건 등록/수정 | 거부 | 명시적으로 배정된 작업에 한해 허용 | 허용 |
| CSV 전체 적재 | 거부 | 거부 | 허용 |
| 데이터 초기화·샘플 복원 | 거부 | 거부 | 허용 |
| 기준 코드 관리 | 거부 | 거부 | 허용 |
| 계정 생성·비활성화·역할 및 담당 작업 배정 | 거부 | 거부 | 허용 |
| 감사이력 조회 | 거부 | 거부 | 허용 |

작업담당자 입력은 현 프로젝트에 존재하지 않는 신규 API·화면이다. 역할이 `WORKER`라는 사실만으로 전체 작업을 수정할 수 없으며, 서버가 각 작업지시에 대한 배정 여부를 확인한다. 조회 범위를 전체로 할지 팀별로 제한할지는 운영 정책으로 확정한다. 미인증 요청은 401, 인증됐으나 권한이나 담당 범위가 없으면 403으로 응답한다.

## 3. 권장 데이터 모델

현재 업무 데이터는 로컬 JSON/엑셀 기반이다. 아래는 **새로 설계할 저장 구조**이며, 기존 엑셀 시트에 실제 존재하는 테이블이 아니다. 계정·권한·감사를 업무용 CSV에 섞지 않고 서버가 관리하는 트랜잭션 저장소에 둔다. 로컬 SQLite는 후보이며 최종 저장 방식은 기존 데이터와 감사기록의 원자적 변경, 백업·복구 요구를 검증해 결정한다.

| 제안 테이블 | 주요 필드 | 제약·용도 |
| --- | --- | --- |
| `roles` | `role_id`, `role_code`, `role_name` | `role_id` PK, `role_code` UNIQUE. 허용 코드 `VIEWER`, `WORKER`, `ADMIN` 세 개를 초기 등록한다. 권한 정책은 서버에서 관리한다. |
| `users` | `user_id`, `login_id`, `display_name`, `role_id`, `is_active`, `created_at`, `updated_at` | `user_id` PK, `login_id` UNIQUE, `role_id`는 `roles` FK. 사용자당 한 역할. 로컬 비밀번호를 쓰는 경우에만 안전한 비밀번호 해시를 별도 저장하며 평문·샘플 암호는 넣지 않는다. 외부 인증 사용 시 인증 제공자의 식별자를 별도 설계한다. |
| `user_work_order_assignments` | `user_id`, `work_order_id`, `assigned_at`, `assigned_by` | `(user_id, work_order_id)` 복합 PK. 사용자와 작업지시를 연결해 작업담당자의 허용 범위를 명시한다. `assigned_by`는 관리자 사용자 ID. 작업지시는 기존 `work_orders`를 참조한다. |
| `audit_events` | `audit_id`, `occurred_at`, `actor_user_id`, `action`, `target_type`, `target_id`, `batch_id`, `result`, `before_ref`, `after_ref` | 관리자 변경·배정, 업로드, 초기화·복원, 실적·사건 변경을 추적한다. 변경 전후 값이나 복원 가능한 스냅샷을 참조하며 비밀번호·토큰은 기록하지 않는다. 대량 변경은 배치 단위로 묶는다. |

`work_orders`가 JSON에 남는 동안에는 DB 외래키로 해당 작업의 존재를 강제할 수 없다. 이 경우 서버가 배정 시 및 변경 요청 시 작업 존재 여부를 검증하고, 작업 삭제·초기화·복원 시 배정 관계를 어떻게 처리할지 정해야 한다. 업무 데이터까지 동일 DB로 이관한다면 트랜잭션과 FK로 관리할 수 있다. 데이터와 감사기록을 별도 파일에 각각 쓰는 방식은 장애 시 두 기록이 어긋날 수 있으므로 원자적 저장 또는 검증된 복구 절차가 필요하다.

### 담당 범위 판단

1. 서버가 로그인 세션에서 사용자 ID와 활성 상태를 확인한다.
2. `ADMIN`은 허용된 관리 작업을 수행하고 `VIEWER`는 읽기만 수행한다.
3. `WORKER`가 실적을 입력하면 해당 `work_order_id`가 본인 배정 목록에 있는지 검사한다. 사건 수정은 서버에서 기존 사건의 작업지시를 조회해 배정 여부를 확인한다. 사용자가 보낸 담당조 문자열을 권한 근거로 사용하지 않는다.
4. 입력값 검증과 저장, 감사 기록은 서버에서 처리한다. UI에서 버튼을 숨기는 것은 편의 기능이다.

## 4. 구현 순서와 완료 기준

| 순서 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 저장 방식과 운영 정책 결정 | 인증 방식, 최초 관리자 생성, 담당 범위, 사용자 비활성화, 감사 보존기간·백업을 정한다. 기존 엑셀·JSON을 자동 수정하지 않는다. |
| 2 | 세 역할·계정·배정 데이터 모델 | 세 역할, 고유 로그인 ID, 계정 활성 여부와 작업별 배정을 저장하고 관리자가 변경할 수 있다. |
| 3 | 서버 인증·인가 | 조회와 업로드·초기화·복원·계정관리·감사 API에 서버 권한을 적용한다. 화면 역할 선택을 로그인 사용자 정보로 대체한다. |
| 4 | 담당 실적·사건 입력 | 담당자 입력 API와 화면을 새로 만들고, 서버에서 배정된 작업만 처리한다. 관리자는 전체 범위를 처리한다. |
| 5 | 감사 및 서버 검증 연결 | 모든 허용 변경에 인증된 사용자와 대상·전후 정보를 남기고, 저장과 감사 기록이 실패 시 함께 롤백되거나 복구된다. 기존 업로드 검증 계획을 함께 적용한다. |
| 6 | 검증·문서화 | 역할별 401/403/허용, 배정된 작업과 타 작업, 비활성 사용자, 직접 API 접근, 업로드 실패·초기화·복원·권한 변경의 감사 및 장애 복구를 격리된 테스트 저장소에서 확인한다. |

인증 방식·사용자 생성과 암호 초기화, 역할 변경 승인, 작업 배정 관리, 팀 데이터와의 연결 여부, 감사 보존기간은 현재 엑셀로 결정할 수 없다. 위 권한표와 모델은 협의용 제안이다. 서버 운영요약은 이 설계 범위에 포함하지 않는다.
