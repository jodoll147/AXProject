# 서버 업로드 검증 구현 계획

작성일: 2026-10-27. 대상은 CSV 업로드 검증, 권한관리 및 감사이력이다. 이 문서는 구현 계획이며, 아래 항목을 이미 구현했다는 뜻은 아니다. 서버 운영요약과 AI 요약은 이번 계획에서 제외한다.

이 문서는 구현 전 계획을 보존한다. 이후 구현된 내용과 남은 제한은 [로그인·권한·감사](로그인_권한_감사.md)를 기준으로 확인한다.

## 목표와 현재 상태

브라우저에서 검사한 데이터를 서버가 저장하기 전에 독립적으로 다시 검증한다. 직접 API를 호출하더라도 같은 규칙이 적용되고, 오류가 한 건이라도 있으면 해당 테이블의 요청 전체를 저장하지 않는다. 기존 데이터와 샘플 엑셀은 자동 수정하지 않는다.

현재 [Program.cs](../app/backend/Program.cs)는 명세 기반 헤더, 필수값, 자료형, 일부 FK와 PK 중복을 검사하고 오류 시 저장을 중단한다. [화면 템플릿](../work/screen_template.html)은 추가로 일부 시간 순서·상태·단위·수량을 검사하지만, 이 검사는 API 직접 호출로 우회할 수 있다. 서버는 `PK / FK`로 함께 표시된 필드의 FK 검사를 건너뛰며, 시간 입력을 저장할 때 초와 시간대 표시를 잘라낸다. 서버와 화면 사이의 규칙 차이가 핵심 보강 대상이다.

현재 업로드 화면의 역할은 브라우저 선택값일 뿐 서버 인가가 아니다. 업로드 이력은 브라우저 세션에만 존재하고 데이터의 변경자·변경 전후 값은 저장하지 않는다.

## 통합 우선순위와 선행 관계

| 순서 | 필수 작업 | 범위와 완료 기준 |
| --- | --- | --- |
| 1 | 인증·인가의 기준과 저장 설계 | 계정 식별, 역할별 API 권한, 최초 관리자 생성, 데이터와 감사 기록을 함께 안전하게 저장하는 방식을 정한다. 테스트용 계정을 고정 자격증명으로 배포하지 않는다. |
| 2 | 서버 기본 검증과 저장 안전성 | 아래 P0의 기본 검증·시간 보존·전체 배치 취소를 구현한다. 기존 데이터는 사전 진단하며 자동 수정하지 않는다. |
| 3 | 인증·역할별 권한 | 서버가 모든 데이터 API에 권한을 적용한다. 화면 역할 선택을 실제 로그인 상태로 바꾸고 API 직접 호출도 통제한다. |
| 4 | 영구 감사이력 | 업로드, 초기화, 샘플 복원과 향후 허용된 데이터 변경의 수행자·시각·대상·결과·전후 값을 보존한다. 데이터와 감사 기록의 저장 실패 시 일관성을 보장한다. |
| 5 | 핵심 업무 검증과 화면 연동 | 아래 P1의 단위·상태·시간·수량·1:1 검증을 서버에서 적용하고 화면에 오류를 표시한다. |
| 6 | 관계·품질 규칙 및 통합 검증 | 아래 P2의 미합의 정책을 확정해 적용하고, 인증·인가·감사·업로드를 함께 검증한다. |

순서 2~4는 하나의 데이터 변경 경로에 연결되는 필수 범위다. 권한이 없는 요청을 거부하고, 허용된 변경은 검증과 감사 기록이 함께 완료되어야 성공으로 응답한다. 순서 6의 세부 규칙은 합의 결과에 따라 조정하되 기능 전체를 생략하지 않는다.

## 권한관리 구현 범위

명세의 역할 제안을 기준으로 다음 권한을 출발점으로 한다. 작업담당자에게 제공할 구체적인 입력 화면과 담당 범위는 현 구현에 없으므로 운영 정책을 확정해 적용한다.

| 역할 | 조회 | 업로드·초기화·복원 | 담당 실적·사건 입력 | 계정·코드 관리 및 감사 조회 |
| --- | --- | --- | --- | --- |
| 조회자 | 허용 | 거부 | 거부 | 거부 |
| 작업담당자 | 허용 | 거부 | 담당 범위에 한해 허용 | 거부 |
| 관리자 | 허용 | 허용 | 허용 | 허용 |

- 서버에 로그인·로그아웃·현재 사용자 확인과 역할 정책을 추가하고, 인증되지 않은 요청은 401, 권한이 없는 요청은 403으로 구분한다. `GET /api/data`, `GET /api/spec`, 상태 및 감사 조회, `POST /api/data/upload`, 초기화·복원과 향후 입력 API를 빠짐없이 검사한다. 헬스 엔드포인트의 공개 범위는 별도 결정한다.
- 사용자 식별자는 서버에서 확정한다. 요청 본문의 사용자명, 브라우저 역할 선택값으로 권한이나 감사 수행자를 결정하지 않는다. 비밀번호를 사용하는 경우 안전한 해시·세션 수명·쿠키 보호 및 CSRF 대응을 설계한다.
- 최초 관리자 생성·계정 비활성화·역할 변경 절차와 담당 팀/작업 범위의 관리 주체를 정한다. 암호 저장 방식, 계정 회복 및 운영 배포 환경은 구현 전에 결정한다.
- 작업담당자의 담당 실적·사건 입력은 **신규 서버 API와 화면이 필요한 범위**다. 허용 필드·생성/수정 범위와 담당자 배정 정책을 확정한 뒤 구현하고, 서버에서 해당 범위를 강제한다. 임의의 CSV 전체 적재 권한을 작업담당자에게 부여하지 않는다.

## 감사이력 구현 범위

- 업로드, 초기화, 샘플 복원, 실적·사건 생성/수정, 계정 및 권한 변경을 기록 대상으로 한다. 요청 실패·권한 거부 기록 정책은 보안과 개인정보 요구를 확인해 정한다.
- 기록에는 사건 ID, 서버 기준 발생시각, 인증된 수행자 ID, 작업 종류, 대상 테이블·키, 성공/실패, 변경 전후 값 또는 변경 내용을 추적할 수 있는 참조를 포함한다. 비밀번호·세션 토큰 등 비밀값은 저장하지 않는다.
- 업로드는 배치 ID와 행별 추가 내용을 연결한다. 초기화·복원처럼 대량 변경은 변경 전후 스냅샷 또는 이에 준하는 복원 가능한 참조를 기록해 실제 변경 내용을 추적할 수 있게 한다. 실패한 업로드는 데이터에 반영하지 않는다.
- 관리자만 감사이력을 조회할 수 있도록 기간·수행자·작업·대상 검색과 상세 조회를 마련한다. 보존기간·삭제 권한·백업·민감정보 노출 범위는 운영 정책을 결정한다.
- **저장 일관성:** 현재 데이터 파일과 별도 감사 파일을 각각 쓰는 것만으로는 장애 시 원자성을 보장할 수 없다. 단일 트랜잭션 저장소(예: 로컬 SQLite) 또는 장애 복구가 검증된 단일 저널 방식을 선택한다. 실제 운영 DB 도입 여부와 별도로 이 선택이 필요하며, 데이터 이관 전 백업과 기존 JSON/샘플 복원 호환성 계획을 마련한다. 감사 저장에 실패하면 변경 성공으로 응답하지 않으며, 중단 후 재시작 시 데이터와 감사 기록이 일치해야 한다.

| 순위 | 작업 | 상세 범위 | 완료 기준 |
| --- | --- | --- | --- |
| P0 | 검증 기반과 저장 안전성 | 현재 검증을 분리 가능한 서버 검증 함수로 정리한다. 요청 본문·헤더 중복과 누락, 유효한 숫자, 모든 FK를 검사하고 기존 응답 형식을 유지한다. 시간 초 단위가 손실되지 않도록 입력·저장·조회 표현을 정한다. 검증 후에만 저장한다. | 정상 요청은 기존 흐름대로 적재하고 오류 요청은 400과 행·필드·사유를 반환한다. 검증 실패 전후 저장 파일의 내용이 같다. |

아래 P0~P3은 **업로드 검증 내부 우선순위**다. 위 통합 순서와 함께 적용한다. P2의 구체 규칙은 업무 정책을 확인한 뒤 적용한다.

## P0: 기본 검증과 저장 처리

1. **API 계약 유지:** 요청 `{ table, headers, rows }`, 성공 응답 및 오류 배열 `{ row, field, rule, msg }`를 유지한다. `row`는 헤더 1행, 데이터 2행부터 시작한다. 기존 화면의 서버 오류 표시는 실제 응답 직렬화 이름을 확인해 그대로 연결한다.
2. **요청 형태:** 알 수 없는 테이블, 빈 배치, 누락·중복·미정의 헤더, 잘못된 행 필드를 거부한다. 선택 필드의 빈 값은 기존처럼 결측으로 처리하고 숫자 0과 구분한다. 크기 제한은 별도 정책이 정해진 경우에 적용한다.
3. **자료형:** INTEGER는 유효한 정수, REAL은 유한한 숫자를 허용한다. 날짜 필드와 시간 필드의 형식을 명세 기준으로 검사하고 유효하지 않은 달력 날짜도 거부한다.
4. **키와 참조:** PK를 정규화한 동일 기준으로 요청 내 및 기존 데이터와 비교한다. `equipment_snapshot.equipment_id`처럼 PK와 FK가 겹치는 필드도 참조 대상을 검사한다. 같은 테이블 내 참조는 기존 행과 요청의 유효한 행을 함께 고려한다.
5. **시간 보존:** `+09:00`과 초를 포함하는 입력의 정보를 버리지 않는 저장 형식을 적용한다. 기존 엑셀과 JSON의 시간대 없는 KST 형식도 읽을 수 있도록 호환성을 확인한다. 기존 저장 자료를 일괄 변환하지 않는다.
6. **원자성:** 모든 검증을 끝낸 후에만 기존의 잠금과 임시 파일 교체를 이용해 저장한다. 실패 시 일부 행을 추가하지 않는다. 현재의 잠금은 단일 서버 프로세스 범위이므로 다중 프로세스 동시 쓰기는 별도 운영 설계가 필요하다.

## P1: 우선 적용할 업무 규칙

| 대상 | 검사 규칙 | 오류 예 |
| --- | --- | --- |
| `work_orders`, `production_actual`, `production_plan` | 작업 단위는 공정 단위와 일치하고 계획·실적 단위는 해당 작업 단위와 일치 | `piece` 작업의 실적 단위가 `m` |
| `production_actual` | 신규 인정수량은 0 이상이며 유한한 숫자 | 음수 증분 |
| 시간 구간과 사건 | 계획·실제·실적·설비·보수의 시작이 종료보다 늦지 않음. 발생·해소도 같은 순서 적용 | 종료시각이 시작보다 빠름 |
| `production_plan` | 작업지시당 계획 1건: 기존 데이터와 현재 요청 모두 확인 | 서로 다른 계획번호로 같은 작업에 두 건 적재 |
| 상태·이벤트 | 해당 도메인의 상태코드, 사건 유형, 작업 이벤트의 허용값 검사 | 정의되지 않은 설비 상태 또는 사건 유형 |
| `incidents` | `OPEN` 사건에 해소시각이 있으면 오류 | 진행 중인 사건에 해소시각 입력 |
| `inspections` | 합격 수 + 불합격 수 = 검사 위치 수. 각 위치 수는 음수가 아님 | 검사 10, 합격 8, 불합격 3 |

시간이 같은 시작·종료를 허용할지, `RESOLVED`에 해소시각을 필수로 할지, 수량 상한과 계획량 0 허용 여부는 정책 확인 후 명시한다. 선행 작업의 **실제 완료 전 후행 시작 금지**는 지연·동시작업 등 예외가 있을 수 있어 P1에서 임의로 강제하지 않는다.

## P2: 정책 확인 후 구현할 범위

- **선후관계:** 선행 ID 자기 참조와 순환을 차단할지, 같은 블록이어야 하는지, 공정 순서와 실제 완료 시각을 어떻게 비교할지 결정한다. 기록이 늦게 입력되는 경우도 고려한다.
- **품질·실적:** 검사 합격·불합격과 재작업의 연결 및 수량 정합성, 검사 재차수 중복, 보수완료 후 재검사 판정 전의 처리 기준을 정한다. 보수 위치수를 생산실적에 자동 가산하지 않는다.
- **상태 이력:** 상태와 해소시각, 설비 구간의 겹침·빈 구간, 상태 전이 허용 범위를 정의한다. 과거 데이터의 누락을 오류로 막을지 판단한다.
- **기존 데이터:** 강화된 규칙이 이미 적재된 데이터나 명세 샘플과 충돌하는지 먼저 읽기 전용으로 진단한다. 기존 불일치를 자동 삭제·수정하지 않는다.

## 검증 계획

격리된 임시 저장소와 명세/샘플 복사본을 사용하는 테스트 환경을 마련해 사용자의 `local-data.json`을 변경하지 않는다. API 통합 테스트와 검증 함수 테스트에서 아래를 확인한다.

| 검증 | 확인할 결과 |
| --- | --- |
| 정상 업로드 | 정상 행이 한 번만 적재되고 기존 응답 및 조회가 유지된다. |
| 직접 API 오류 | 단위 불일치, 잘못된 상태, 역순 시간, 중복 계획 등은 행·필드·사유를 반환한다. |
| 기본 경계 | 필수 공란과 0, 중복/누락 헤더, 무한대·잘못된 날짜, 기존 및 같은 배치의 중복과 참조를 구분한다. PK 겸 FK 누락을 거부한다. |
| 배치 원자성 | 정상 행과 오류 행을 함께 보내도 전체가 거부되고 저장 파일의 내용이 변하지 않는다. |
| 시간 호환성 | 초가 있는 `+09:00` 입력이 손실 없이 조회되고 기존 엑셀/KST 문자열을 읽는다. |
| 화면 연동 | 서버 오류가 올바른 셀·행에 표시되고 수정 후 재검증·업로드가 가능하다. |
| 회귀 확인 | 명세 샘플 및 기존 초기화·복원 흐름을 테스트 환경에서 확인한다. |
| 인증·인가 | 미인증 401, 역할 부족 및 담당 범위 밖 403, 권한이 있는 요청의 성공을 화면과 직접 API 호출 모두에서 확인한다. |
| 감사이력 | 수행자·대상·전후 값, 업로드/초기화/복원 기록과 관리자만 조회 가능한 정책을 확인한다. 실패·거부 기록은 합의한 정책에 따라 검사한다. |
| 장애 복구 | 감사 저장 실패, 데이터 저장 실패, 저장 중 중단 및 재시작을 주입해 데이터와 감사이력의 불일치가 없음을 확인한다. |

## 산출물과 완료 조건

- 서버 검증, 인증·역할별 인가, 영구 감사이력, 담당 실적·사건 입력을 구현하고 API 통합 테스트와 관련 화면·문서를 갱신한다.
- 검증 규칙별 정상·오류, 역할별 접근, 감사 기록 및 장애 복구 사례가 통과하고 저장 원자성과 시간 보존을 확인한다.
- 계정 운영, 담당 범위, 감사 보존기간과 P2 규칙은 구현 전에 확정한다. 기존 데이터의 불일치는 진단 결과로 보고한다.
