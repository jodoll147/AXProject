# 데이터베이스·데이터 모델

## 1. 현재 저장 방식

전용 DBMS는 없습니다. 처음에는 `엑셀 파일/02_조선_샘플데이터.xlsx`를 읽습니다. 초기화 후에는 `app/backend/local-data.json`을 로컬 적재 저장소로 사용하며 샘플 엑셀 원본은 보존합니다. ASP.NET Core 백엔드가 데이터를 JSON으로 전달합니다.

엑셀 원본과 목업 CSV·ZIP은 Git에 포함하지 않습니다. 로컬 실행 시 필요한 엑셀 파일은 별도로 준비해야 합니다.

`엑셀 파일/01_조선_데이터참고명세서.xlsx`는 데이터 참고 명세이며, `엑셀 파일/조선_AX_목업데이터.xlsx`는 별도 목업 데이터 파일입니다. 현재 React API의 기본 원본은 `02_조선_샘플데이터.xlsx`입니다.

## 2. 시트(테이블) 목록

| 시트 | 데이터 영역 |
| --- | --- |
| `vessels` | 호선 식별자와 명칭 |
| `zones` | 작업 구역 |
| `processes` | 공정 식별자, 구역, 순서 등 공정 기준정보 |
| `equipment` | 설비 기준정보와 공정 연결 |
| `blocks` | 블록 기준정보, 호선 및 목표 이송 |
| `status_codes` | 상태 코드와 한글 레이블 |
| `work_orders` | 공정별 작업지시, 계획 수량·일정·설비 등 |
| `production_plan` | 생산 계획 데이터 |
| `production_actual` | 기간별 생산 실적 변화량 |
| `equipment_intervals` | 설비 상태의 시작/종료 구간 |
| `incidents` | 설비·자재·품질 사건과 발생/해소·담당 기록 |
| `work_history` | 작업 상태 이벤트와 시각/메모 |
| `inspections` | 검사 및 불합격 위치 데이터 |
| `rework` | 재작업·보수 구간 및 연결 정보 |
| `equipment_snapshot` | 설비의 기준시각별 상태 및 점유 작업 |

## 3. 개념 관계

```text
호선(vessels) ──< 블록(blocks) ──< 작업지시(work_orders) >── 공정(processes)
                                        │                       │
                                        ├── 실적(production_actual)
                                        ├── 계획(production_plan)
                                        ├── 작업이력(work_history)
                                        ├── 사건(incidents) ── 검사(inspections)
                                        │                  └── 보수(rework)
                                        └── 설비(equipment) ── 상태구간(equipment_intervals)
                                                               └── 스냅샷(equipment_snapshot)
구역(zones) ── 공정/설비
상태 코드(status_codes) ── 상태값 설명
```

위 그림은 화면 코드가 사용하는 업무상 연결을 나타냅니다. 실제 파일 안의 관계 제약(외래 키)은 엑셀에서 강제되지 않습니다.

## 4. 데이터 로딩과 JSON 변환

- 백엔드는 `app/backend/local-data.json`이 있으면 이 파일을 우선 읽고, 없으면 `엑셀 파일/02_조선_샘플데이터.xlsx`를 읽습니다.
- 서버가 고정한 15개 시트 이름을 차례로 엽니다. 첫 사용 행을 헤더로 사용합니다.
- 빈 헤더 열과 빈 셀은 결과 행에서 생략하며, 값이 하나 이상 있는 행만 반환합니다.
- 날짜형 셀은 `yyyy-MM-ddTHH:mm`, 정수형 숫자는 정수, 소수는 숫자, 논리값은 Boolean, 그 외는 문자열로 반환합니다.
- 화면은 샘플 엑셀의 시간대 없는 `yyyy-MM-ddTHH:mm`과 CSV의 `yyyy-MM-ddTHH:mm:ss+09:00`을 모두 한국시간 기준으로 해석합니다.
- 시트가 없거나 파일이 없으면 로드가 실패합니다. 시트 이름/헤더가 코드의 예상과 달라지면 데이터 조회가 정상 동작하지 않을 수 있습니다.

## 5. 캐시와 기준시각

백엔드는 현재 데이터 파일의 UTC 수정 시각을 저장하고, 수정 시각이 같으면 메모리에 저장한 테이블을 반환합니다. 파일 수정 시 다시 읽습니다. 로드·적재·초기화 구간은 lock으로 보호됩니다. CSV 업로드는 검증을 통과한 전체 행을 로컬 JSON 파일에 기록합니다.

프론트엔드는 `equipment_snapshot` 중 가장 늦은 `as_of`를 화면 기준시각으로 사용합니다. 기준시각 이후의 작업 이력, 실적, 사건은 화면 집계에 반영하지 않습니다. 따라서 파일에 기준시각이 갱신되어야 화면 계산도 갱신됩니다.

## 6. 파생 데이터

- 작업 상태: 기준시각까지 시간순으로 정렬한 마지막 작업 이벤트를 상태 코드로 변환합니다. 기록이 없으면 예정입니다.
- 인정 수량: 기준시각까지의 `accepted_qty_delta` 합계.
- 진척률: 인정 수량 ÷ 계획 수량, 최대 100%로 제한.
- 미해소 사건: 발생 시각이 기준시각 이전이고 해소 시각이 없거나 기준시각보다 뒤인 사건.
- 설비 시간: 조회 기간과 상태 구간의 겹치는 길이를 상태별로 합산합니다.

## 7. 무결성 및 현재 한계

- 엑셀은 형식 제약, 외래 키, 트랜잭션, 동시 편집 제어를 제공하지 않습니다. 행 식별자와 참조 무결성은 데이터 작성자가 유지해야 합니다.
- CSV 업로드는 로컬 JSON에만 기록하며 샘플 엑셀 파일을 수정하지 않습니다. 로컬 파일을 초기화하거나 샘플로 복원할 수 있습니다.
- 운영 DB 전환 시 테이블 키, 관계, 시간대/단위, 변경 이력, 중복/누락 검증, 동시 갱신 정책을 별도로 설계해야 합니다.
