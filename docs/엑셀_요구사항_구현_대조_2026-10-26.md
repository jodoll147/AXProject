# 데이터 참고 명세서와 현재 구현 대조 (2026-10-26)

> **현재 대조 기준:** [요구사항 기준본 및 화면·알고리즘 구현 대조](요구사항_기준본_및_구현대조_2026-10-28.md). 이 문서는 작성 당시의 조사·계획 이력으로 보존한다.

## 범위와 판정 기준

- 원본: 사용자 제공 `01_조선_데이터참고명세서.xlsx`의 10개 시트 전체. 시트의 내용은 비교 기준이며, 이 문서의 문구를 작업 지시로 취급하지 않았다.
- 대상: 현재 실행 진입점 `app/frontend/index.html`(생성 원본 `work/screen_template.html`), `work/sync_frontend.mjs`, `app/backend/Program.cs`, 로컬 샘플 `app/backend/local-data.json` 및 프로젝트 문서. `app/frontend/src/`의 React 코드는 현재 진입 화면에서 사용하지 않으므로 구현 판정에서 제외했다.
- **구현**: 현재 실행 경로에 기능이 있음. **부분 구현**: 핵심 흐름은 있으나 명세의 조건·표시·검증 중 일부가 빠짐. **미구현**: 실행 경로에 기능이 없음. **자료/협의**: 명세가 참고자료 또는 추후 결정 대상으로 적은 내용.
- 코드와 샘플 데이터의 정적 조사 결과다. 브라우저 조작이나 API 요청으로 끝단 동작을 재검증하지 않았다.

## 전체 결론

기본 데이터 조회, 현황 지표, 블록·작업·설비·사건 상세, 실적 증분 집계, 생산 지연, CSV 업로드 및 규칙 기반 요약은 구현되어 있다. 그러나 명세와 **완전히 일치하지는 않는다**. 특히 서버의 업무 규칙 검증, 좌표 기반 2D 배치, 실제 권한, 서버 계산 요약, 과거 시각 재생이 빠졌거나 제한되어 있다. 아래 표는 명세의 요청 대응표, 기능·화면, 업무 시나리오, 운영요약, 구현 참고사항을 모두 대조한 것이다.

## 2. 데이터구성·테이블관계·항목명세

### 2.1 데이터 구조 및 사용 여부

명세의 15개 테이블은 모두 로더와 로컬 데이터에 있다. 조사 시 `local-data.json` 행 수는 명세의 예시 행 수와 전부 일치했다. 이는 **데이터가 존재한다는 확인**이며 각 행의 의미나 모든 FK가 유효하다는 전수 증명은 아니다.

| 테이블 | 명세/로컬 행 수 | 현재 사용·표시 | 판정 |
| --- | ---: | --- | --- |
| `vessels` | 2 | 호선명, 블록 그룹, 정규식 검색 | 구현 |
| `zones` | 6 | 구역명·설비 그룹 사용, `x/y` 좌표 미사용 | 부분 구현 |
| `processes` | 6 | 공정 순서·명칭·단위 사용, `standard_hours` 미사용 | 부분 구현 |
| `equipment` | 8 | 설비 목록·상세·공정·구역·자원구분 | 구현 |
| `blocks` | 12 | 호선, 블록명, 중량, 도면 개정, 목표 이송 | 구현 |
| `status_codes` | 14 | 상태 한글 표시 및 화면 검증 | 구현 |
| `work_orders` | 72 | 일정·상태·설비·선후행·수량·예상 완료. 현재 상태와 실적은 이력/증분에서 재계산 | 구현 |
| `production_plan` | 72 | 적재·참조 및 1:1 화면 검증은 있으나 계획 대비 화면 집계는 주로 `work_orders.planned_*`를 사용. `plan_date`, `plan_version`, `planned_qty` 별도 활용 없음 | 부분 구현 |
| `production_actual` | 133 | 종료시각 기준 증분 합산, 최근 증분 및 누적 표시 | 구현 |
| `equipment_intervals` | 201 | 상태 구간, 점유율, 고장·점검 시간 | 구현 |
| `incidents` | 5 | 유형·발생/해소·담당·조치·연결 작업 | 구현 |
| `work_history` | 94 | 이벤트 기반 작업 상태, 상세 이력 | 구현 |
| `inspections` | 7 | 검사 차수·합격/불합격 상세 | 구현 |
| `rework` | 1 | 보수 시간·위치수·상태 상세 | 구현 |
| `equipment_snapshot` | 8 | 최신 기준시각, 현재 설비 상태·점유 작업 | 구현 |

관계는 화면의 ID 맵과 그룹으로 연결되며, CSV 업로드에서는 명세의 FK 문자열을 읽어 기존 데이터 또는 같은 배치의 참조를 검사한다. 다만 파일 원본 로딩 시 무결성 검증은 하지 않고, DB 수준 FK/고유/1:1 제약도 없다. 특히 `production_plan` 작업지시당 1건 규칙은 **화면 검증에만** 있고 서버는 해당 FK와 PK만 검사한다. [screen_template.html](../work/screen_template.html) 1126행; [Program.cs](../app/backend/Program.cs) 139–204행.

105개 항목의 필드명·자료형·필수 여부·PK/FK 메타데이터는 `/api/spec`으로 읽는다. 업로드 서버는 정수/실수, `*_at` 시간, 필수값, PK 중복과 FK를 검사한다. 항목별 의미·범위·상태·단위·선후관계까지 **모두** 강제하는 구현은 아니다.

| 서버 계산값으로 요약 작성 | 미구현 | 집계와 요약 문장은 브라우저의 `metrics()`/`summaryRows()`에서 생성한다. 서버의 AI 요약 엔드포인트는 비활성 응답이다. |

| 키·필수·단위·상태·시간순서 검증 | 부분 구현 | 화면에는 다수가 있으나 서버에는 단위·상태·시간순서 검증이 없다. 시간 형식만 검사한다. |

## 6. 누락·차이 우선 정리

> 아래는 2026-10-26 조사 당시의 우선순위다. 이후 구현한 로그인·권한·감사·서버 검증 및 계획/실적 상세의 현재 상태는 [2026-10-27 잔여 요구사항과 다음 작업](잔여_요구사항_진행계획_2026-10-27.md)을 참고한다. 서버 운영요약은 이후 사용자 요청으로 범위에서 제외했다.

1. **서버 업로드 검증 보강:** 단위 일치, 허용 상태·범위, 시작≤종료, 계획 1:1, 작업 선후, 품질/실적 정합성을 서버에서도 검증해야 화면을 우회한 잘못된 적재를 막을 수 있다. 현재 화면 검증도 공정 선후와 일부 테이블 단위 검증이 빠져 있다.
2. **권한과 감사:** 계정·인증·역할별 API 인가, 담당 범위 입력, 변경자·변경시각·전후 값 기록이 없다. 현재 역할 선택은 보안 통제가 아니다.
3. **운영요약의 서버 계산 및 실제 AI 여부 결정:** 명세의 작성 기준과 현재 브라우저 계산 방식이 다르다. 실제 AI를 목표로 한다면 모델 연동·근거 검증이 별도 필요하다. 고장시간 문장은 `equipment_intervals`의 관측 구간 합계로 고쳐야 한다.
4. **계획·실적 상세 확대:** `production_plan`의 버전/계획일/당일 계획량 대비 `production_actual` 기간별 실적을 같은 공정·단위로 볼 수 있어야 한다.
5. **배치도 좌표 반영:** 현 화면은 개념 공정 그리드다. 명세의 `zones.x/y` 기반 2D 배치가 필요하면 좌표 기반 배치로 바꿔야 한다.
6. **과거 시각 재생 UI:** 관측 이력 절단 로직은 있으나 사용자가 기준시각을 바꾸는 화면·동작은 없다.

## 확인 범위와 제약

- 샘플 데이터의 15개 테이블 행 수와 주요 샘플 지표를 독립 계산해 확인했다. 데이터 원본의 105개 필드별 값과 24개 관계를 모두 전수 검증하지는 않았다.
- 브라우저 화면 조작, API 업로드 실패/성공 호출, 빌드·테스트는 이 조사에서 실행하지 않았다. 따라서 “구현”은 실행 경로와 샘플 데이터의 정적 근거에 대한 판정이다.
- 명세의 실제 공장 도면, 기존 제품 화면, 운영 DB·권한 범위는 제공되지 않은 참고/협의 대상이므로 그 자체를 현재 앱의 오류로 단정하지 않았다.
