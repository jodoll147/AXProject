# 운영요약 알고리즘 및 코드 보고

> 기준: 2026-10-28 현재 `app/frontend/index.html`과 `app/backend/Program.cs` 구현. 화면의 명칭은 **운영요약 초안**이다. 외부 AI 호출이나 자연어 모델 추론은 없다.

## 1. 데이터 흐름

1. 로그인 세션을 `/api/auth/me`로 확인한다. 로그인하지 않으면 업무 화면을 렌더링하지 않는다 (`index.html` 737–746행).
2. `/api/data`, `/api/spec`, `/api/data/status`를 병렬 요청한다. `ready`가 거짓이면 업무 테이블을 빈 배열로 바꾼다 (747–753행).
3. 시간 문자열에 시간대가 없으면 `+09:00`을 붙여 밀리초로 파싱하고, 작업지시·실적·사건·검사·보수를 ID별로 묶는다 (757–765행).
4. 최신 `equipment_snapshot.as_of`를 기준시각 `AS_OF`로 택한다. 스냅샷이 없으면 관측 이벤트들의 최대시각, 관측값도 없으면 `Date.now()`가 된다 (`history_state.js`의 `observationBounds`, `index.html` 782–785행). 초기 표시 시각 `t`는 `AS_OF`다.
5. `summaryRows()`가 기준시각의 지표와 사건별 문장을 구성하고, `renderSummary()`가 편집 가능한 화면을 만든다 (1423–1462행).

요약은 브라우저에서 계산한다. 서버의 `/api/summary/ai`는 `{ enabled: false, text: null }`만 반환한다 (`Program.cs` 423행).

## 2. 기준시각의 작업 상태와 지표

`woAt(w)`는 작업지시별로 `event_at <= t`인 작업이력의 마지막 이벤트를 읽어 상태를 정한다. 이벤트가 없으면 `PLANNED`이고, `START`·`RESUME`·`REWORK_DONE`은 `IN_PROGRESS`, `PAUSE`·`QUALITY_HOLD`는 `BLOCKED`, `COMPLETE`는 `COMPLETED`다 (`index.html` 778, 806–820행). 인정수량은 `period_end_at <= t`인 `production_actual.accepted_qty_delta`의 합이다. 진척은 `min(1, 인정수량 / 계획수량)`이다. 이 계산에는 계획수량 0에 대한 별도 분기나 하한 0 제한이 없으므로, 비정상 수량이 들어오면 표시가 이상해질 수 있다.

```js
const his = (HIS[id] || []).filter(h => h.event_at <= t);
const acts = (ACT[id] || []).filter(a => a.period_end_at <= t);
const acc = acts.reduce((s, a) => s + a.accepted_qty_delta, 0);
const status = his.at(-1) ? EVENT_STATUS[his.at(-1).event_type] : 'PLANNED';
const progress = Math.min(1, acc / w.planned_qty);
```

`metrics()`는 전체 작업을 현재 시각으로 재구성한다 (`index.html` 842–851행).

| 요약 항목 | 실제 판정 |
| --- | --- |
| 금일 계획 작업 | `planned_start_at`의 한국 날짜가 `t`의 날짜인 작업 |
| 그중 완료 | 위 작업 중 재구성 상태가 `COMPLETED` |
| 기한 도래 | `planned_end_at <= t` |
| 기한 도래 미완료 | 기한 도래 작업 중 상태가 `COMPLETED`가 아님 |
| 미해소 사건 | `opened_at <= t`이고 `resolved_at`이 유효하지 않거나 `t`보다 늦음 |

완료율은 금일 계획 작업이 있을 때만 `완료 수 / 계획 수 × 100`이며 소수 첫째 자리로 반올림한다. 기한 도래 수와 미완료 수는 **현재 기준시각의 상태**를 사용한다. 마감 뒤 완료된 작업은 지연 조회에는 나타날 수 있지만 운영요약의 ‘미완료’에는 포함되지 않는다.

## 3. 문장 생성 순서와 조건

`summaryRows()`의 출력은 `{facts, asks}` 두 배열이다 (`index.html` 1423–1442행).

1. **기준시각:** 데이터가 준비되면 `YYYY-MM-DD HH:mm KST · 최신 데이터 기준`, 없으면 `데이터 없음 · 업로드 전`.
2. **운영 현황:** 금일 완료/계획, 기한 도래/미완료, 미해소 사건 수를 한 문장으로 작성. 계획 작업이 0건이면 완료율 괄호를 생략.
3. **미해소 사건별 사실:** 사건마다 한 행을 작성. 사건은 `CAT`에 선언된 유형 순서인 설비 → 자재 → 품질로 정렬된다. 동일 유형 내 별도 정렬은 없다.
4. **회복 상황:** `resolved_at <= t`이고 해소 날짜가 기준일인 사건마다 한 행을 작성. 완료된 작업은 완료 시각, 그 외는 현재 진척을 표시한다. 예상 완료는 최신 기준시각이며 미완료이고 `forecast_end_at`이 있을 때만 쓴다.
5. **확인 요청:** 현재 미해소 사건마다 담당 팀을 행 제목으로 하여 유형별 복구 예상시각·자재 공급시각·재검사 판정을 확인하도록 적는다.

### 유형별 문장 규칙

| 유형 | 사용 필드와 계산 | 표현 |
| --- | --- | --- |
| 설비 고장 (`EQUIPMENT`) | 작업번호, 설비번호(있는 경우), 사건 요약, 발생시각, 작업 진척, `t − opened_at` | ‘관측 고장시간’으로 경과시간을 표시하고 사건 ID를 첨부 |
| 자재 대기 (`MATERIAL`) | 작업번호, 발생시각, 사건 요약, 진척 | 설비 고장 시간에 포함하지 않는다고 명시하고 사건 ID 첨부 |
| 품질 보류 (`QUALITY`) | 같은 작업·사건 ID의 기준시각 이전 마지막 검사, 기준시각 이전 시작한 마지막 보수, 작업 인정수량 | 검사 위치/불합격 수 또는 사건 요약, 보수 진행/완료 후 재검사 대기, 인정수량 유지, 사건·보수 ID 첨부 |

품질 검사 선택은 `inspected_at <= t && incident_id 일치` 후 마지막 항목이다. 보수 선택은 `start_at <= t && incident_id 일치` 후 마지막 항목이며, 보수 종료가 기준시각 이내이면 ‘보수는 완료했으나 재검사 판정 전’이라고 쓴다. 그렇지 않으면 ‘보수 진행 중’이다. 문장에 쓰는 인정수량은 `woAt`이 계산한 증분 합이다. 별도 품질 차감 계산은 없다.

```js
const q = (QC[id] || [])
  .filter(x => x.inspected_at <= t && x.incident_id === i.incident_id).at(-1);
const r = (RW[id] || [])
  .filter(x => x.incident_id === i.incident_id && x.start_at <= t).at(-1);
const rw = r
  ? (Number.isFinite(r.end_at) && r.end_at <= t
      ? '보수는 완료했으나 재검사 판정 전이므로'
      : '보수 진행 중이며')
  : '';
```

시각은 한국 시간으로 표시한다. `pct()`는 소수 첫째 자리 백분율, `num()`은 소수 첫째 자리 수량, `dur()`은 경과 분을 반올림해 분 또는 시간/분으로 표시한다 (`index.html` 789–800행). 따라서 경과시간은 설비 구간의 합계가 아니라 **사건 발생부터 기준시각까지의 경과**다.

## 4. 근거 링크, 편집, 복사

문장 속 `[INC…]`, `[INC… / RW…]`는 `refLinks()`가 작업 상세 `#/wo/{work_order_id}` 링크로 바꾼다 (`index.html` 1444행). 링크는 해당 사건·보수가 연결된 작업으로 이동한다. 화면에서 ‘관측 사실’과 ‘확인 요청’은 별도 영역이며 각 행은 `contenteditable`이다.

편집 내용은 `sumEdits`라는 브라우저 메모리에 저장된다. 같은 기준시각의 재렌더에서는 유지되지만 시각 `t`가 바뀌면 지워진다. ‘초안으로’는 편집을 지우고 재생성한다. ‘복사’는 화면의 모든 행을 `제목\t본문` 형식으로 이어 클립보드에 기록하며 공백을 정리한다 (`index.html` 1445–1461행). 서버 저장, 변경 이력, 내보내기 파일은 구현되어 있지 않다.

## 5. 해석과 검증 경계

- 문장은 입력 데이터의 **관측 사실**과 누락된 정보의 **확인 요청**만 다룬다. 사건 원인, 복구시각, 공급시각을 추정하지 않는다.
- ‘관측 고장시간’은 실제 설비 고장 구간 총합이 아니다. 사건이 해소되지 않았다는 전제에서 `t − opened_at`을 쓴다.
- `summaryRows()`는 상태와 실적을 매번 기준시각으로 재계산하지만, 사용자 편집은 서버에 저장되지 않는다.
- 코드 경로를 정적으로 대조했다. 이 문서 작성 과정에서 특정 CSV를 넣어 요약 결과값을 재현하는 통합 테스트는 실행하지 않았다.

## 6. 입력 테이블과 요약 문장 간 연결

아래 표는 요약이 실제로 읽는 값을 문장 단위로 역추적한 것이다. 계획·이력·실적은 먼저 작업지시 번호로 연결되고, 검사·보수는 작업지시 번호에 사건 번호까지 맞춰 선택한다.

| 입력 | 주요 필드 | 요약에서 쓰이는 곳 | 시각 조건 |
| --- | --- | --- | --- |
| `work_orders` | `work_order_id`, `planned_start_at`, `planned_end_at`, `planned_qty`, `unit`, `forecast_end_at` | 금일 계획, 기한 도래, 작업별 진척·예상 완료 | 계획 시작은 기준일 비교, 종료는 `<= t`; 예상 완료는 최신 기준에서만 문장에 사용 |
| `work_history` | `work_order_id`, `event_type`, `event_at` | 마지막 작업 상태, 완료 시각 | `event_at <= t` |
| `production_actual` | `work_order_id`, `accepted_qty_delta`, `period_end_at` | 인정수량 합계, 진척률 | `period_end_at <= t` |
| `incidents` | `incident_id`, `work_order_id`, `category`, `opened_at`, `resolved_at`, `summary`, `owner_team`, `equipment_id` | 미해소 사건, 유형별 사실, 회복 상황, 확인 요청 | 발생 `<= t`; 해소는 유효하고 `<= t`일 때 인정 |
| `inspections` | `work_order_id`, `incident_id`, `inspected_at`, `checked_points`, `failed_points` | 품질 보류의 검사 결과 | 같은 사건, 검사 `<= t`의 마지막 기록 |
| `rework` | `parent_work_order_id`, `incident_id`, `rework_id`, `start_at`, `end_at` | 품질 보류의 보수 상태와 근거 ID | 같은 사건, 시작 `<= t`; 종료 `<= t`이면 보수 완료 문구 |
| `equipment_snapshot` | `as_of` | 기본 기준시각 상한 | 유효한 스냅샷 중 최신 시각 |

`equipment_intervals`는 기준시각 범위를 정할 때 관측 자료로 참조되지만, 운영요약의 사건별 ‘관측 고장시간’을 계산하는 데에는 사용하지 않는다. `processes`, `blocks`, `vessels`도 요약 문장 본문에서 직접 집계하지 않는다. 이들은 다른 화면과 작업 연결에 쓰인다.

## 7. 코드 실행 순서를 따라 본 상세 추적

### 7.1. 기준시각 확정

`observationBounds()`는 작업 이력, 실적 구간, 사건, 설비 구간, 검사, 보수, 설비 스냅샷에서 유효 시각을 모은다. 유효 스냅샷이 하나라도 있으면 최신 `as_of`가 관측 상한이다. 계획 시작·마감 및 예상 완료 시각은 이 범위를 늘리지 않는다. 화면 초기 진입은 이 상한 `AS_OF`에서 시작한다. 운영요약은 현재 전역 시각 `t`를 읽으므로, 별도의 독립적인 보고 시각을 입력받지 않는다.

### 7.2. 작업 단위 상태 재구성

작업 `W`에 대해 먼저 `HIS[W]`의 이력을 시각순으로 정렬한 뒤, `t` 이내 마지막 이벤트를 `EVENT_STATUS`에 대응한다. 실적은 `ACT[W]`에서 종료시각이 `t` 이내인 증분을 더한다. 사건은 발생시각이 `t` 이내인 것만 추리고, 해소시각이 없거나 `t` 뒤이면 열린 사건으로 남긴다. `st()`는 같은 `t` 안에서는 작업별 계산값을 메모이제이션하고 `t`가 달라질 때 캐시를 비운다 (`index.html` 803–820행).

### 7.3. 전역 지표 계산

```js
const ws = D.work_orders.map(w => st(w.work_order_id));
const today = ws.filter(s => ymd(s.w.planned_start_at) === ymd(t));
const due = ws.filter(s => s.w.planned_end_at <= t);
const open = D.incidents.filter(i =>
  i.opened_at <= t && !incidentResolved(i, t)
);
const todayDone = today.filter(s => s.status === 'COMPLETED');
const overdue = due.filter(s => s.status !== 'COMPLETED');
```

여기서 `ymd()`는 `Asia/Seoul` 날짜를 반환한다. 따라서 UTC 날짜가 바뀌는 경계에서도 ‘금일’은 한국 날짜로 판정한다. 미해소 사건은 작업 상태가 완료인지와 별개로 사건의 해소시각으로 판정한다. 완료 작업에 해소되지 않은 사건이 남아 있다면 사건은 여전히 요약에 들어간다.

### 7.4. 문장 조립과 화면 출력

`summaryRows()`가 `[라벨, 문장]` 행을 만든 뒤 `renderSummary()`가 HTML을 생성한다. 문장 속 사건·보수 번호는 작업 상세 링크로 바뀐다. 수정 시 `innerText`를 `sumEdits`에 보관해 같은 기준시각에서 화면이 다시 그려져도 유지한다. 복사는 현재 화면에 보이는 수정본을 읽는다. 즉 **복사 결과는 원래 규칙 문장과 달라질 수 있다**.

## 8. 계산 예시 — 설명용 가상 데이터

다음 값은 구현 규칙을 설명하기 위해 만든 예시이며, 저장소의 실제 CSV 결과값이 아니다.

- 기준시각 `t`: 2026-09-16 12:00 KST.
- 금일 착수 계획 작업 4건 중 기준시각 상태가 `COMPLETED`인 작업 2건.
- 계획 마감이 기준시각까지 도래한 작업 3건 중 `COMPLETED`가 아닌 작업 1건.
- 09:30에 발생했고 아직 해소되지 않은 설비 사건 1건. 연결 작업의 계획량은 10, 기준시각까지 인정수량 증분은 2와 3.

계산은 `금일 완료 2/4 = 50.0%`, `기한 도래 3건 중 미완료 1건`, `미해소 사건 1건`이다. 연결 작업의 인정수량은 `2 + 3 = 5`, 진척은 `min(1, 5/10) = 50.0%`다. 사건 발생부터 기준시각까지는 150분이므로 `dur()`는 `2시간 30분`을 반환한다. 이 2시간 30분은 설비 상태 구간을 합산한 값이 아니다.

예시 출력 형태는 다음과 같다. 사건 요약 내용은 실제 데이터 필드 그대로 삽입된다.

```text
운영 현황  금일 계획 작업 2/4건 완료(50%). 기한 도래 3건 중 1건 미완료. 미해소 사건 1건.

확인 요청  WO-예시1 복구 예상시각 확인 필요. 자료에 없어 추정하지 않음. [INC-예시1]
```

실제 화면에서는 `pct()`가 `50%`처럼 불필요한 소수 `.0`을 표시하지 않는다. 위 예시 계산 설명의 `50.0%`는 반올림 자릿수를 보이기 위한 수학적 표기다.

## 9. 조건별 출력과 검토 기준

| 상황 | 구현 결과 | 사용자 검토 지점 |
| --- | --- | --- |
| 업로드 데이터가 비어 있음 | 기준시각 행에 ‘데이터 없음 · 업로드 전’; 운영 현황은 0/0과 0건 | 데이터를 먼저 적재했는지 확인 |
| 금일 계획 작업 0건 | `0/0건 완료`를 쓰고 완료율 괄호 생략 | ‘실적 0%’로 해석하지 않기 |
| 사건이 발생했지만 기준시각 전에 해소됨 | 미해소 사실·확인 요청에서 제외; 기준일에 해소됐으면 회복 상황에 포함 | 해소 날짜와 기준시각 확인 |
| 사건 해소시각이 기준시각보다 늦음 | 기준시각에서는 미해소로 취급 | 미래 해소 기록을 현재 사실로 읽지 않기 |
| 품질 사건에 검사 기록이 없음 | 사건 요약을 대신 표시 | 검사 자료 누락 여부 확인 |
| 보수 기록은 있으나 종료가 기준시각 뒤임 | ‘보수 진행 중’ | 실제 종료 및 재검사 판정 확인 |
| 사건에 설비 번호가 없음 | 설비 번호 부분만 생략 | 원본 사건의 연결 정보 확인 |
| 요약 본문을 수정함 | 같은 기준시각의 화면 메모리에 남고 복사에 반영 | 별도 저장 기능이 없어 필요한 곳에 붙여 넣기 |

운영요약은 사건·실적을 검토하기 위한 초안이다. 자동으로 보고서를 승인하거나 발송하지 않으며, 수정된 문장을 데이터 원본에 되돌려 저장하지 않는다.
